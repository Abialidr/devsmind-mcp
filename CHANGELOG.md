# Changelog (compact)

> Full prose version with rationale for each change: [detailExplanation.md § Changelog](detailExplanation.md#changelog). This file is the scan-fast version — one line per change.

## 4.0.0 — One write path, a server-driven indexer, and memory that writes nothing
> **Breaking.** `stage_change` is removed — `edit_node` is now the only write tool. The in-chat indexing protocol changed shape. Re-run `devsmind rule` after upgrading; a rule written against an older version still tells your agent to call a tool that no longer exists.

- **`stage_change` removed, folded into `edit_node`.** It covered code `edit_node` couldn't trace by being *told* (`node_id`/`type`/`code_snapshot` supplied by hand) instead of *discovering* it from where a write landed. DevsMind has been TS/JS-only since before this release, and `edit_node`'s tracing already covers all of it, so the split no longer earned its keep. Every rule/memory/instruction reference to "which write tool" now just says `edit_node`. Forcing a graph resync with no real code change (the one thing `edit_node` structurally can't do — it requires `old_string` to differ from `new_string`) is now `devsmind reindex`'s job.
- **In-chat indexing (`index_start`/`index_continue`/`index_checkpoint`/`index_complete`) rebuilt around local AST extraction.** The server now parses structure itself, deterministically, no LLM — the same machinery `devsmind index --run` already used. No code crosses back to the server anymore; the AI's only job is writing descriptions via `add_description` (which now also takes an optional `type`, to upgrade the AST's generic type to a framework-specific one). Connections still resolve once over the whole graph in `index_complete`, resumably. `index_checkpoint` is a zero-argument progress read now.
- **`devsmind memory` writes nothing, for any tool.** Research across all 9 integrated tools found background/automatic memory to be discretionary by design almost everywhere — several tools say so in their own docs. It now prints one natural-language "remember this" prompt to paste into any AI chat instead; `--tool <id>` only changes the framing line, not the prompt content.

## 3.0.1 — `get_activity_log` answers on a fresh clone, and Codex gets seeded like Antigravity
> No breaking changes and no tools removed. `devsmind memory` is worth re-running if you use Codex — it now has somewhere to write.

**Fix: `get_activity_log` returned nothing for anyone but the person who made the commits.** It read one store — the local activity log — which is gitignored by design, because it holds verbatim request text and full before/after backups that have no business in a shared repo. The cost of that was invisible until someone else asked: a teammate on a fresh clone, or you on a second machine, got a flat empty result for "what changed here lately?" while `.devmind/history/` had been recording exactly that all along, committed and pulled. Empty is the worst possible answer — it reads as "nothing happened," not "I looked in the wrong place." A new `source` param resolves it and **defaults to `auto`**: local first, falling through to committed history only when local has nothing. `source:"both"` is the team-wide view — your own entries in full fidelity plus every commit that did not happen on this machine — and exists because `auto` alone doesn't fix the inverse case: once you have any local activity of your own, it stops at the local store and you still never see a teammate's work. `local`/`graph` force one store.
- **How a commit is recovered from shared history.** History is stored per NODE, but one `commit_changes` hands the same `reasoning` object to every node in the batch, so they all carry a byte-identical block — that text is the commit identity. `session_id` is deliberately *not* part of the key even though it looks like the obvious one: the 1-hour merge writes a later block into an existing row and keeps that row's *original* session id, so within a single commit one node reports the session that created its row while another reports the current one. Keying on it would split one real commit in two. What separates two commits that happen to share reasoning text is time — blocks from one commit land milliseconds apart — so grouping cuts on the gap between *consecutive* blocks, never total span, which keeps a slow many-node commit intact however long it ran.
- **Graph-backed answers say what they can't tell you.** They carry a `caveats` array rather than passing off a thinner entry as an authoritative one: `status` is always `applied` (revert state is a local-log concept), `request` degrades to the reasoning's `Requirement` field because the verbatim ask is never committed, and whole-file edits that traced to no node are absent.
- **`source:"both"` de-dupes your own work on session id AND developer, in that order of evidence.** Session alone gets it wrong: the merge can file a teammate's block under one of *your* session ids, and hiding a teammate's commit is exactly the failure `both` exists to fix. The `Developer` field is written per block and survives the merge intact, so it settles the disagreement. The asymmetry is deliberate — showing your own work twice is visible and harmless; dropping someone else's is not.
- **Fix: `total_messages` counted *after* `limit`.** A capped result was indistinguishable from a complete one — ask for 10 out of 50 matches and it answered `10`, with nothing to say more existed. A new `total_matched` reports the true pre-`limit` count, the same honesty contract `nodes_total`/`getHistoryPage().total` already keep. Present on both stores.

**Codex is seeded automatically now, exactly like Antigravity.** It was marked unsupported because the only Codex store anyone had looked at was `~/.codex/memories/` — generated state its own docs warn against hand-editing, which a background job rewrites. That is still never touched. But Codex has a second, human-authored surface, and it reads `.agents/skills/devsmind/SKILL.md` — **the same file Antigravity already writes**. So this was less a new integration than pointing a third target at an existing one: seeding for either tool now covers both. Antigravity, Antigravity CLI and Codex share a single scope and a single frontmatter wrapper, because these writes are whole-file — per-tool wrappers would mean seeding one tool silently rewrote the file the others read, last command wins. A test asserts all three render identical bytes, and another asserts no memory scope ever resolves into `~/.codex/memories/` (or Windsurf's/Qwen's equivalents). No new flags: same picker, same preview, same confirm.

**`devsmind memory` stops rewriting files that are already correct.** Re-running it walked the full preview-and-confirm flow to write bytes identical to what was on disk. It now compares first and reports `✅ Already seeded — up to date`, which matters more than it sounds now that two tools share one file: seeding Antigravity genuinely does finish the job for Codex, and the command should say so. It deliberately does *not* short-circuit when the pointer file is stale — Claude Code's topic files load only via the index in `MEMORY.md`, so current topics with a missing index is a broken install, not a finished one, and a corrupted-marker merge returns the file unchanged in a way that would otherwise read as a match and swallow the error.

## 3.0.0 — Workflows rebuilt around sessions, search that survives one turn, no more `devmind_path`
> **Upgrading from 2.4.0 — the last version actually published.** A 2.5.0 was prepared and never released, so everything it contained ships here instead: the rebuilt `devsmind view` app, the activity log with revert, explicit sessions, and the two rule workflow styles. Those are listed under *"Also in 3.0.0"* below. If you were on 2.4.0, this one jump covers all of it.
>
> A major, not a minor: tools were **removed** (`workflow_pause`/`resume`/`search`/`get_steps`/`add_artifact`/`read_artifact`/`sync_retroactive`, `get_node_graph`, `get_node_history`), `search_nodes` lost `keywords`/`is_regex`, and `list_nodes` now answers an object instead of a bare array. Re-run `devsmind rule` **and** `devsmind memory` after upgrading — an agent working from the old rule will call tools that no longer exist.

**Fix: `get_visualizer_url` handed back a URL that 404s.** It returned a `visualizer_2d` *and* a `visualizer_3d` (`/3d?path=…`), left over from when those were separate pages — but the view app became a single page with a 2D/3D toggle inside the Graph tab, and the `/3d` route went away with it. Anything following the 3D link got a 404. One `url` now, plus a note saying where the toggle actually lives. Also aligned three JSDoc comments that still said port **4500** while every line of code used **4513**.

**Fix: `devsmind mcp` could corrupt an existing Codex `config.toml`.** Deciding whether our server table was already in the file used a substring test on the whole file, then located it with an exact line match — two different questions. A config that merely *mentioned* the header (`# see [mcp_servers.devsmind] docs`, or the same text inside a string value) passed the first and failed the second, leaving the index at `-1`: the file's last line got dropped and everything after the mention was re-emitted, so every following table appeared **twice**. Duplicate tables are a TOML parse error, so the merge handed back a config Codex could no longer read — and it happened on a path that otherwise looks like a clean success. Both checks are now the same check. The whole placement layer — `mergeRuleFile`/`mergeMcpConfig`/`writeConfigFile`, the pickers above them, and the tool registry — had **no tests at all**, because it reads from a TTY. It has 123 now: the merge functions directly, the pickers by driving the single `prompts` call they all funnel through (including the directory navigator, which is what turns a menu into an absolute path), and an integration pass that pushes the REAL generated rule and a real MCP registration through every one of the 9 tools' own registry entries. `prompt.ts` and `registry.ts` are now in the coverage gate, at 100% lines and branches.

**`devsmind memory` works non-interactively — `--print`, like `devsmind rule --print` always had.** It hard-exited on a non-TTY, so `devsmind memory > memory.md` was impossible and there was no way to read what it seeds, diff it against a store you already have, or produce it from a script. The rendering already existed (it's what the interactive flow's "just show me what to add" mode prints); it simply had no route in. `--tool <id>` picks which store's shape to print — `claude-code` for the one-file-per-fact shape, `antigravity`/`antigravity-cli` for the single combined document — and without it, it prints the Claude Code shape and *says* it defaulted rather than picking one silently. An unknown tool, or a real one with no seedable store, gets told which tools do have one.

**`devsmind init` stopped appending duplicate `.gitignore` entries, and stopped reflowing your file.** It compared entries as raw strings, so a hand-written `local` was never recognized as already covering `local/` — and since the entry list only grows, every re-init piled another near-miss on top (`/dist` vs `dist/` had the same problem elsewhere). Matching is now by what git actually reads a line as, so `local`, `/local`, `local/` and `/local/` all count as the same thing. Separately, the old version read the file, dropped every blank line, and wrote the survivors back — silently reflowing a `.gitignore` someone had grouped and commented, on a run that was meant to be a no-op. It now appends under a labeled block and never rewrites what's already there. The activity log's own self-heal (which adds `local/` on first write, for a brain that never re-runs `init`) shared the same string-matching flaw and now uses the same rule, so the two can't disagree about whether something is already ignored. `.devmind/.gitignore` had **no test coverage at all**, which is how this survived; it has 15 tests now, including one asserting the list still covers every local-only path and still leaves `graph/`, `history/`, `vectors/` and `workflows/` shared.

**`devsmind -v` reports the real version.** It answered `1.0.0` from the first commit through the entire 2.x line — hardcoded next to `package.json`'s real number, and never once updated. Worse than no version at all: someone filing a bug reads it and believes it, and so does whoever tries to reproduce against that release. The CLI, the MCP server's `serverInfo`, and `GET /health` now all derive from `package.json`, so there is one number and nothing to keep in sync.

**Workflows rebuilt around sessions — 12 tools down to 8, and a real bug fixed.** "Which workflow is active" was a **single project-wide pointer** that was also serialized into the committed `workflow.json` and restored on sync. So two sessions shared one: session B calling `workflow_resume` silently paused session A's mid-work, and A's next `commit_changes` wrote its step onto **B's** timeline — no error — and because the pointer travelled through git, a teammate could do it to you. Binding is now **per session and local** (`.devmind/local/`), so it never moves, pauses, or steals anyone else's, and two sessions can work different workflows at once. A workflow is what it always should have been: a named, backward-looking log of how one piece of functionality grew.
- **Steps record `reasoning` + `node_ids`** instead of `history_ids`. The old link could not identify a commit at all — two commits touching one node within an hour merge into a *single* history row, so a step's ids could point at rows an earlier commit made, and one row could be cited by several steps. Reasoning is copied onto the step rather than joined, because history reasoning *mutates* afterwards (the merge appends, revert can drop a block) — a record of "what we thought at the time" cannot read from a moving target.
- **`workflow_add_step` now covers research**, which nothing else in DevsMind captured: git has the diff and history has the per-node reasoning, but neither records *what was evaluated and rejected*. One call takes the finding and the docs behind it (`doc_paths`) — stored as **paths, not copies**, so they can't go stale, with a path outside the repo rejected since it wouldn't exist for a teammate.
- **`workflow_sync` actually syncs.** The old `workflow_sync_retroactive` read nothing — the agent hand-assembled a `steps` array from its own context. It now reads your local activity log, previews what it would attach, and only writes on `confirm:true`. Re-running is a no-op (dedupe is by consumed edit id, so a message that keeps growing can still contribute later without doubling anything).
- **`workflow_get_context` is paged and size-guarded** (it had *no* cap: every step, every artifact, and optionally every artifact file inlined whole). It absorbed `workflow_get_steps`; artifact content is no longer inlined at all — you get the file path.
- **`workflow_list` gained `query`**, matching name *and* description — the search `workflow_search` never did (it scanned step summaries and artifact names only, so looking a workflow up by its own name returned nothing).
- **`archived` replaces `status`.** Nothing ever "completed" and nobody marked it, so the field lied; threads sort by last-touched and archiving only claims what it delivers — hide this from the list, reversibly.
- **Fixes:** `commit_changes` never passed `session_id` when creating a step, so the column existed and sat null on the path that creates nearly every step; `workflow_create` claimed to pause the previous workflow and didn't, leaving several rows marked active at once.
- **A teammate on an older build can no longer destroy the new data.** Each workflow is now written as two files: `workflow.json` in the shape a v1 client understands, and `v2.json` holding what v1 has no field for (`archived`, per-step `reasoning`/`node_ids`/`doc_paths`). `devsmind sync` re-serializes every `workflow.json` from local columns, so an un-upgraded machine that pulled and synced *would* have rewritten the file without the new fields and committed that loss — it has no idea the sidecar exists, so it cannot touch it, and the next read merges everything back. A corrupt or missing sidecar degrades to the v1 shape rather than losing the workflow.
- **`devsmind revert` leaves no trace again.** A history row cited by a workflow step used to be emptied rather than deleted, so the step was not left pointing at nothing. Steps record `node_ids` now, so nothing references a history row at all — the guard had nothing to check, and keeping it would have meant keeping the `history_ids` column alive to protect a reference nobody makes.
- **Gone:** `workflow_pause`/`workflow_resume` (→ `workflow_bind`, retained as unadvertised aliases), `workflow_get_steps` (→ `workflow_get_context`), `workflow_search` (→ `workflow_list` `query`), `workflow_add_artifact`/`workflow_read_artifact` (→ `doc_paths` + file paths), `workflow_sync_retroactive` (→ `workflow_sync`). **Breaking:** existing workflows migrate automatically on the next brain open. The one caveat is that backfilling old steps' node lists is approximate — see [WORKFLOW_DESIGN.md](WORKFLOW_DESIGN.md#migration).

**Indexing stopped asking an LLM to *find* your code — it only asks it to judge.** The old extractor sent a whole file's source with "extract all code structures, return JSON", so the model was responsible for both **finding** every function and **deciding** which mattered. That conflates two very different jobs, and it fails silently at the first one: a function the model overlooked simply never became a node, with nothing to indicate anything was missed. Now the AST enumerates every declaration deterministically (`enumerateFileCandidates`), and **existence is never delegated to a model**. Anything **exported** is auto-accepted with **zero LLM turns** — on a typical file that's most of it, so many files touch the LLM not at all. Only the genuinely ambiguous remainder (an unexported helper, an anonymous default, a tiny inline callback) goes to a **tool-calling agent** that decides keep / drop / merge / rename, can pull the file's imports mid-decision for context, and must call `submit_decisions` to finish. If it runs out of turns, every undecided candidate defaults to **keep** — over-including is recoverable, silently dropping a real entity is not. That rework is also why `--chunk-size`/`--chunk-overlap` became no-ops: chunking existed to stop a big file overflowing one whole-file call, and the file stopped being the unit of work.

**Search results stop being crowded out by lockfiles — and your configured file exclusions finally work.** `ignored_paths` was only ever checked against **directories**, so every FILE in it was silently searched anyway. That was the common case, not an edge one: `devsmind init`'s own preset list is entirely file names (`package-lock.json`, `yarn.lock`, `tsconfig.json`, …), and `.gitignore` import passes literal file names straight through — users had excluded these, watched them keep appearing in every result, and had no way to tell the exclusion was being dropped on the floor. Lockfiles (`package-lock.json`, `yarn.lock`, `pnpm-lock.yaml`, `Podfile.lock`, `go.sum`, …) and build artifacts (`*.min.js`, `*.min.css`, `*.map`) are now also excluded by default, so a repo that predates `init` still gets clean results — a lockfile names every dependency in the tree, so a product term like "alipay" matched it purely because a package was named that. `.env`, JSON and other config remain fully searchable; that is what the `files` bucket is for. Scoping `path` straight at an excluded file returns nothing and now says so in `scope_note`, instead of reading as "the pattern isn't in there". Also fixes a leading-slash `.gitignore` entry (`/dist`, `/build`) matching nothing at all, in both the search walk and the indexer. **Behavior change:** if your `ignored_paths` lists files, they will now genuinely disappear from search results — that is the setting finally taking effect.

**`list_nodes` is paged — it had no bound of any kind.** It returned every matching node as full pretty-printed rows, so on a real backend a single unfiltered call was ~600KB across ~10,900 lines: past the client's inline limit, spilled to a file, and truncated on read from there too. It now answers `{nodes, total, offset}` with `total` as the true match count and `nodes` as one page (`limit`, default 100, max 500), plus `truncated` and a `hint` naming the exact next call whenever there is more — an enumeration tool is precisely the one that must be paged, since the reason you're asking is that you don't know how many there are. Pages are ordered by file path then name, so they never overlap or skip. A page that is still oversized (long descriptions) falls back to id/name/type/file_path per node with a `compacted` note, `total` still exact. **Breaking:** the response is now an object rather than a bare array. Paging is opt-in at the library level, so internal whole-graph consumers (`analyze`, edge resolution) are unaffected.

**Oversized responses no longer dead-end.** A large `search_nodes` result could exceed the client's inline limit, spill to a file, and have *that* file truncate on read too — leaving nothing usable. Results are now trimmed automatically when they would be too big, in two steps: first dropping bulk-without-signal (per-file `match_counts`, `matched_terms`, `aliases`, repeated `used_by_note` boilerplate) and thinning sample lines, and only giving up the evidence lines entirely if that isn't enough. A `compacted` field always states which happened, and **every count stays exact**, so a trimmed result is never mistakable for a complete one. `compact:false` demands the full payload; `compact:true` asks for a lean triage list up front. Compaction also *skips* the AST symbol-annotation pass rather than computing it and throwing it away. Responses are no longer pretty-printed — indentation was 20-30% of the payload and MCP clients parse rather than read it.

**`get_node_code`'s `graph_code` fits in one turn, and names what didn't.** The char budget defaults to 24000 (was 60000) when embedded in a `get_node_code` response, since it rides along with code, imports, neighbors and history rather than being the whole payload. When the budget runs out, the dropped nodes are listed **by id** in `graph.code_omitted_node_ids` — fetch exactly those, or re-issue with a larger budget. Ids rather than a positional cursor on purpose: the walk is re-derived per call and the cut-off also depends on file contents, so an index would silently skip or repeat nodes. `nodes_without_code` previously conflated "budget ran out" with "the source genuinely could not be found"; the second is now reported separately as `nodes_no_code_available`, because raising the budget will never bring those back. The root's code is no longer duplicated inside the graph (it is already on the top-level `code`). The graph walk is now deterministic, so two identical calls return identical results.

**Fixes: several numeric params were unvalidated in ways that failed silently.** `graph_code_budget:"abc"` (and legacy `code_char_budget`) became `NaN`, and since every `spent + len > NaN` comparison is false, that meant an **unlimited** budget — the exact opposite of passing a budget. `search_nodes`' `limit:"abc"` became `NaN` too, and `slice(0, NaN)` returned an empty `files` array next to a non-zero `files_total`, indistinguishable from "grep found nothing"; a negative `offset` paged from the *end* of the ranking, and `limit` had no upper bound at all (now max 200). Adds a missing index on `node_connections(target_node_id)` — every "who uses X" lookup was a full table scan, once per node visited in a graph walk.

**`search_nodes` results lead with their trust signals.** Each node now emits `confidence`/`relevance`/`found_by` ahead of `description` instead of after it. The fields always existed, but landing behind a full sentence of prose meant they got skipped in favor of eyeballing node names — and a name that merely looks right is the easiest way to pick the wrong node.

**`search_nodes` — real regex, path scoping, honest totals/pagination, containing-symbol insight.** `keywords` (a pipe/comma-split list that got regex-ESCAPED before matching) is **removed** in favor of `pattern`: a REAL regex used exactly as given, the same string you'd hand `grep`. The old escaping silently mangled a caller's own correct regex (e.g. `item\.liked` searched for a literal backslash and never matched real code) — this is the fix. `query` is now **optional**: a `pattern`-only call is a first-class precision mode that skips the semantic/BM25/identifier-shortcut layers entirely (a regex has no meaning to embed), returning exact grep + code-body matches only. New optional `path` scopes the walk to one folder/file instead of every configured repo — rejected outright if it falls outside every repo; the ignore list (`node_modules` et al.) still applies inside a scope, so a scope pointing straight at an ignored dir returns nothing. `case_insensitive` (previously accepted but silently ignored, same as the old dead `is_regex`) is now actually wired through. Every `files`-bucket sample line reports the containing function/class when resolvable (`symbol`) — insight a plain filesystem grep can't give. Both buckets stay bare arrays (nothing wrapped), but now carry true `files_total`/`files_offset`/`nodes_total` sibling fields, so a capped page is never mistaken for "nothing more to find"; `offset`/`limit` page through the files bucket. **Breaking:** `keywords` and `is_regex` no longer exist on `search_nodes` — re-run `devsmind rule` (and `devsmind memory` if seeded) to pick up the new contract.

**Server binds to one project — no more `devmind_path` on every call.** `devsmind start` (HTTP or `--stdio`) now resolves its one project once at startup (`--path`, or auto-detected from cwd) and every advertised tool schema drops `devmind_path` entirely when bound — the AI never discovers, remembers, or re-sends it. Generated stdio configs bake in an absolute `--path` (the IDE controls the spawn cwd, not this project, so cwd auto-detect alone isn't reliable there); HTTP relies on the cwd `devsmind start` was launched from. Unbound (tests, or no `.devmind` found) falls back to the legacy per-call `devmind_path` behavior unchanged.

**`session_id` no longer required on reads.** Searching/reading mutates nothing, so gating it on a session bought nothing but friction — the very first thing an agent tries in a conversation used to error. Now only WRITE tools (`edit_node`, `stage_change`, `commit_changes`, and the other mutating tools) require `session_id`; `search_nodes`, `get_node_code`, `get_node_history`, `get_node_graph`, `list_nodes`, and the other read-only tools work from the first call. `get_activity_log`'s own optional `session_id` filter (a real, deliberate param) is no longer force-promoted to required by the blanket injection this used to go through.

**Fix: `commit_changes` could flush and mis-attribute another session's staged work.** The on-disk staging buffer (`history_scratchpad.json`) is shared by every session pointed at one `.devmind` directory, but `commit_changes` read and cleared **all** of it regardless of who staged what — a session committing its own change could silently sweep in another session's still-in-progress edits (sometimes from an unrelated file, even a different repo), stamp them with the wrong `reasoning`, and either way wipe them from the buffer. `stage_change`/`edit_node`'s `pending_count` had the same flaw, reporting a total inflated by other sessions' work. `add_description` could likewise write a description straight onto another session's staged-but-uncommitted node. All four are now scoped to the calling session (`partitionStagedForSession`/`clearStagedForSession` in `staging.ts`): a plain commit only ever touches its own staged entries, `other_sessions_pending` in the response says whether others exist, and `add_description` refuses outright with a clear error when the target belongs to a different session instead of silently applying or misreporting "no such node". Structural graph writes (`rename_node`, `deprecate_node`, `merge_nodes`, `split_node`, `link_nodes`, `record_alias`, `create_missing_node`) write straight to the single shared committed graph and were never affected — there is no per-session pending state there to protect.

### Also in 3.0.0 — new view app, an activity log with revert, explicit sessions, two rule styles
> This was staged as 2.5.0 and never published to npm, so it ships as part of 3.0.0. Nothing below is separately installable — if you are coming from 2.4.0, you get all of it in one jump.

**`devsmind view` — completely rebuilt.** One app (Chat + Graph tabs) replaces the old three disconnected pages (`/` 2D graph, `/3d`, `/activity`), and it now works fully offline — the D3/three.js/3d-force-graph libraries and Tailwind are vendored into the package and served locally instead of loaded from a CDN.
- **Graph**, redesigned around the actual complaint that the whole-graph view doesn't scale: a sidebar accordion (repo → type, with search) drives what you look at; clicking a node opens a small ego-graph of just its `uses`/`used by` neighbors — distinct colours, directional arrows, a legend, click a neighbor to re-center — instead of the entire graph rendered at once. Every node is labeled (not just a bare colored dot). Filters for type, developer, and an actual date **range** (not just presets), each with "select all / none," and every filter selection persists across reloads. A "See whole graph (2D)" button stays as the escape hatch for when you do want the big picture. 2D/3D toggle on the ego-graph; whole-graph is 2D only.
- **Chat**, a read-only history of `commit_changes` calls rendered like a chat transcript (your request, the AI's summary) grouped into sessions, with a date-range filter defaulting to today. Expanding a message shows a **git-style whole-file diff** — every edit a message made to one file collapses into a single PR-style hunk view, with a "view full file" toggle for the complete reconstructed file, changes highlighted. Revert/un-revert live right there.
- Fix: `view.html` was read and cached once at server start, while its JS/CSS were always read fresh — a server left running across an update could silently serve a stale page paired with newer JS that expected elements the stale page didn't have. Now re-read on every request, with `Cache-Control: no-store` on both.

**Activity log** (`devsmind view` → Chat) — a local timeline of your own work, grouped by session then by request.
- Every `commit_changes` call becomes a **message**; the same request text on a later commit merges it into the existing message instead of scattering across several. Fully local — `.devmind/local/`, gitignored, never pushed, never shows teammates' work.
- **Message-level revert, with a backup** — unlike `devsmind revert` (below), reverting a message here keeps it: code goes back, the message is marked reverted, and un-revert brings it back. **Stack semantics**: revert a message in the middle and everything built on top of it reverts too (newest first); un-revert restores oldest-reverted-first, back up the stack. A revert that hits a file changed since (a hand-edit, a pull) stops at a clean boundary rather than forcing it.
- **Now covers every file, not just traced code** — a CSS/JSON/XML/YAML/Markdown edit, or a code edit landing outside any function (an import line), never gets a graph node (the graph stays code-only, by design) but is now still staged as a whole-file before/after for the activity log, so it's visible and individually revertable in Chat too. When a commit mixes traced code edits and untraced whole-file edits on the *same* file, they're ordered by when they actually happened (not "all code edits, then all file edits") so the whole-file reconstruction undoes them correctly.
- `devsmind activity [--since <days>]` — the same timeline in the terminal, read-only.

**`edit_node` diff + revert** — `edit_node` now returns the diff of what it just changed as a rendered `+`/`-` block right in the tool result (a second content block, so nothing that parsed the old response breaks), and records the code as it stood *before* each edit, which is what makes reverting possible. `devsmind revert <node_id>` / `devsmind diff <node_id>` from the terminal. Only the newest edit to an entity is revertable — refused, not guessed at, when the file's moved on since.

**Explicit sessions** — a new `start_session` tool is now the only way a session comes into being. **Breaking:** `session_id` is required on every DevsMind tool call, reads included (echoed back on every response so it survives a long or compacted conversation); `message` and `reasoning` are required on `commit_changes`, validated *before* anything is written so a rejected call for a missing field is a safe no-op, not a partial commit.

**Reasoning moved from every edit to once per commit.** `edit_node`/`stage_change` no longer take a `reasoning` argument — every edit in one commit almost always serves the same request, so repeating `why`/`goal` on each call was pure duplication. `commit_changes` now takes ONE required `reasoning` object, recorded against every node staged since the last commit. **Breaking:** any `edit_node`/`stage_change` call passing `reasoning` gets it silently ignored (the field no longer exists in the schema); `commit_changes` calls now need a `reasoning` alongside `message`.

**`devsmind rule` — two workflow styles, and a session kickoff prompt.** Choose **Automatic** (unchanged: stages, commits, and tracks every edit without being asked) or **Manual** (search/read tools stay always-on, but the AI only stages/commits when explicitly asked — `--manual` flag for non-interactive use). `session_id`/`message` stay required in both; the style only changes whether the AI *decides on its own* to write. Every run also prints a short, separate **session kickoff prompt** to paste at the start of a fresh chat, worded for whichever style you picked, so a new conversation commits to the rule immediately.

**Paste this before every session, always**, regardless of style — the shortest, strictest version of the reminder above:
> Before doing anything else: fully read and follow this project's DevsMind rule — no exceptions, no shortcuts, not even for a small edit.
> Call `start_session` first and carry its `session_id` on every DevsMind call this conversation, or nothing else will work.

**`devsmind memory` — one file per fact, not one blob.** Claude Code loads a memory file only *on demand*, ranked by that file's own `description` frontmatter, so a single monolithic `devsmind.md` either loaded whole or not at all. It now seeds 15 topic files (`edit_node`, `search_nodes`, `get_activity_log`, the `commit_changes` contract, workflow tools, graph repair, indexing, the CLI surface, …), each with frontmatter and cross-links, so an editing task pulls in the `edit_node` rule without also dragging in indexing trivia — plus an index block in `MEMORY.md` (the file that *does* load every session), replacing the old single pointer line. Antigravity Skills, which load one `SKILL.md` per skill directory, still get everything collapsed into one document from the same source.

- Fix: the seeded Claude Code memory file had no `name`/`description` frontmatter at all — the exact field its store ranks on when deciding what to recall — and its `MEMORY.md` pointer line still described the pre-2.4 contract (`edit_node` for "existing TS/JS code", `stage_change` for "every other edit").
- Fix: `devsmind rule` had drifted from what the MCP server actually enforces — it omitted `commit_changes`' required `feedback` object (so an agent following the rule wrote a call the server rejects outright), described `search_nodes`' pre-rewrite behavior with no mention of `keywords` or the `files` grep bucket, never mentioned `get_activity_log`, and left out `search_decisions`, `get_visualizer_url`, and the graph-feedback/structural-fix tools. New test suite reads the live tool list off a real in-process MCP server and fails when the generated rule or memory drifts from it again.
- Fix (security): agent-authored reasoning was interpolated straight into the visualizer's HTML — markup in `what`/`why`/`goal`/`developer` executed as script. Escaped.
- **Action needed:** re-run `devsmind rule` (and `devsmind memory` if you seeded it) — the tool contract changed (`start_session`, required `session_id`/`message`/`reasoning`/`feedback` on `commit_changes`, no more per-edit `reasoning`) and the rule now also asks which workflow style to use.

## 2.4.0 — `edit_node`: one write path for every file
- New: `edit_node` MCP tool — a single `file_path` + `old_string` + `new_string` + `reasoning` call edits ANY file (never refuses a file type, unlike `stage_change`) and works out which function/class the edit actually landed in, recording it automatically — no `node_id` lookup, no `code_snapshot` echo, no separate `stage_change` call for TS/JS/JSX/TSX/Vue/Svelte. Also creates brand-new files (`old_string: ""`). `stage_change` is now scoped to what `edit_node` can't trace: languages with no local parser (Python, Go, Java, C#, Ruby, PHP, Rust, Swift, Kotlin, Dart).
- Fix (data corruption): the startup path-healer in `syncFromDisk` only recognized `C:`/POSIX paths as "already absolute" — every node's `file_path` on a `D:` drive or a UNC path (`\\server\share\...`) was silently rewritten to the `.devmind` folder path, on every server restart.
- Fix (data corruption): `rename_node` given a bare/unqualified id (the exact form every read tool accepts, e.g. `get_node_code`) silently left the OLD node's history/edges in place and created an empty, disconnected node under the new id — the rename reported success but didn't actually move anything.
- Fix: required string arguments across all 35 tools are now validated before use — a forgotten field now errors with a clear message instead of silently persisting the literal 9-character string `"undefined"` as real data (found via `workflow_create`/`workflow_add_step`, generalized to every tool).
- Fix: `edit_node`/`stage_change` could write to DevsMind's own `.devmind/` directory (config, brain.db, cached graph JSON) — the path-allowlist check computed the wrong root. Now explicitly excluded.
- Fix: `workflow_sync_retroactive` duplicated every step on a retry with an identical payload — now idempotent, matching `workflow_import`'s existing behavior.
- Fix: `search_nodes`, `workflow_search`, and `list_nodes`'s `file_path` filter had unescaped SQL `LIKE` wildcards (a literal `%`/`_` in a real query matched everything) and/or unnormalized path slashes (a forward-slash filter silently matched nothing on Windows).
- Fix: `devsmind analyze` reported real, correctly-indexed files as "untracked" on Windows due to a drive-letter case mismatch — same bug class fixed for `getNodesByFilePath` last release, not previously applied here.
- Fix: `devsmind init` exited 0 with no output under a non-interactive shell instead of failing clearly (now matches `mcp`/`memory`'s existing guard); `devsmind prune` swallowed its own errors so a failure during pruning still exited 0.
- Fix: corrupted (mojibake) emoji/arrow and em-dash characters in `server.ts`, including inside tool-description text sent to every AI model on every session.
